# Замечания для команды бизнес-модели

Инфраструктура разрабатывается параллельно; перечисленные исправления в неё
не включены. Метод проверки: чтение DDL/триггеров и пробное формирование строк
генератора seed=42 с перехватом INSERT-данных, без PostgreSQL. Измеренные ниже
числа относятся к исходной присланной версии, а не к запущенной БД.

## 1. Закупки и приёмки одной партии

Сопоставлялись `purchase_line.batch_bk` и приходные `movement.batch_bk`.
У 3 080 из 3 300 принятых партий не совпал поставщик, у 2 200 — РЦ,
у 3 299 — количество. Заказам назначаются поставщик/РЦ по индексу заказа,
приёмкам — по индексу партии. В закупке количество всегда 300, в приёмке
оно выводится из будущих продаж и запаса.

Пример BATCH-S0000000042-00001-02: закупка от SUP-...-001 в DC-...-01 на 300;
приёмка от SUP-...-002 в DC-...-02 на 512. Требуется единый план поставки.

Запрос для последующего воспроизведения в WMS:

```sql
SELECT pl.batch_bk, pl.purchase_bk,
       po.supplier_bk AS ordered_supplier, m.src_bk AS received_supplier,
       po.dc_bk AS ordered_dc, m.dst_bk AS received_dc,
       pl.quantity AS ordered_quantity, m.qty AS received_quantity
FROM purchase_line pl
JOIN purchase_order po USING (purchase_bk)
JOIN movement m ON m.batch_bk=pl.batch_bk AND m.movement_type='receipt'
WHERE (po.supplier_bk,po.dc_bk,pl.quantity)
      IS DISTINCT FROM (m.src_bk,m.dst_bk,m.qty);
```

Если частичные приёмки вводятся осознанно, сопоставление количеств нужно
выполнять по сумме и добавить соответствующую модель исполнения закупки.

## 2. I9 и фактическая дата приёмки

CHECK защищает `batch.received_at`, но не `movement.moved_at`. Вставка нового
приходного движения существующей партии после expiry_date не отклоняется
соответствующей проверкой. Нужны защита операции приёмки и негативный тест.

## 3. Удаление клиента с продажами

CRM скрывает клиента/карты и очищает контакты. POS продолжает отдавать
прежний customer_bk; после удаления связанного покупателя X04 получит orphan.
P2 создаёт клиента без чеков и сценарий не покрывает. Согласовать процесс
обезличивания/представления продаж и передачу удалений в будущий DWH.
Отдельного запрета DELETE для customer без зависимостей тоже нет.

## 4. Смены

Нет проверки времени чека относительно открытой/закрытой смены. Генератор
создаёт одну смену на аптеку на весь горизонт истории. Требование о документе
в открытой смене стоит реализовать и проверить отдельно от текущего чекера.

## 5. Сценарии, которые нужно описать

- Есть 525 refund-документов, но нет WMS-движений возврата покупателя. Решить,
  моделируется ли только денежный возврат или также приём товара/карантин.
- Схема позволяет region/pharmacy цены, но seed демонстрирует только chain.
- Дельта сейчас создаёт независимые справочники и продажи. Это пригодно
  для проверки репликации, но не демонстрирует обновления существующих строк.

Ни одна из этих задач не требует менять адреса сервисов или физическую
репликацию. Согласовать только имена четырёх баз, сохранение contract API,
путь нумерованных миграций и способ запуска Python-генератора.
