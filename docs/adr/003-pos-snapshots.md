# ADR 003: snapshot изменяемых атрибутов в POS

**Статус:** принято.

## Контекст

Catalog, WMS и POS — разные сервисы. После продажи могут измениться:

- название SKU;
- признак Rx;
- текущая цена;
- состояние партии в других системах.

Исторический чек при этом не должен изменяться задним числом.

Кроме того, I10 должен запрещать продажу Rx без рецепта внутри POS, без синхронного запроса в Catalog.

## Рассмотренные варианты

1. **Всегда читать текущие значения из Catalog/WMS.** Отвергнуто: исторический отчёт будет меняться после обновления справочников.
2. **Проверять Catalog синхронно при каждом DB constraint.** Отвергнуто: cross-database constraint невозможен и появляется runtime-зависимость другого сервиса.
3. **Сохранять нужные значения в момент продажи как snapshot.** Выбрано.

## Выбор

В `receipt_line` физически фиксируются:

- `unit_price`;
- `sku_name_snapshot`;
- `is_rx_snapshot`;
- `batch_expiry_date_snapshot`.

I10 проверяется локально по `is_rx_snapshot` и `receipt.prescription_bk`.

Snapshot expiry позволяет POS локально проверять продажу просроченной партии.

Cross-service checker дополнительно проверяет согласованность snapshot с источниками.

## Цена выбора

Snapshot дублирует данные Catalog/WMS и должен корректно заполняться приложением или генератором.

Зато факт продажи становится исторически стабильным и не зависит от текущего состояния другого сервиса.
