# ADR 006: единая polymorphic movement вместо subtype-таблиц

**Статус:** принято.

## Контекст

WMS должен хранить движения партии между разными типами endpoints: supplier, distribution center, pharmacy, customer и внешнее списание. Часть endpoint-сущностей принадлежит самому WMS, а pharmacy/customer находятся в других сервисах, поэтому единый физический FK на endpoint невозможен.

## Рассмотренные варианты

1. **Отдельные таблицы по каждому маршруту**: supplier→DC, DC→pharmacy, pharmacy→customer, возвраты, writeoff. Отвергнуто: появляется несколько почти одинаковых таблиц, сложнее строить общий журнал, contract.v_movement приходится собирать UNION-ом.
2. **Отдельная универсальная таблица location/endpoints.** Отвергнуто: она всё равно не даёт настоящего FK-контроля для pharmacy/customer из других БД и создаёт дополнительный слой идентичности.
3. **Одна movement с парами type + BK для source/destination.** Выбрано.

## Выбор

Используем одну таблицу `movement` с:

- `movement_type`;
- `src_type/src_bk`;
- `dst_type/dst_bk`;
- `batch_bk`;
- количеством и временными отметками.

Допустимые маршруты ограничиваются DB CHECK по комбинации `movement_type + src_type + dst_type`. Внутренние сущности WMS защищаются обычными FK там, где это возможно; cross-service целостность проверяется генератором и checker.

## Цена выбора

Полиморфная ссылка слабее обычного FK: БД не может сама доказать существование pharmacy/customer. В запросах нужно учитывать endpoint type. Зато журнал остаётся единым, contract простым и расширяемым, а схема не дублирует одинаковые поля по нескольким subtype-таблицам.
