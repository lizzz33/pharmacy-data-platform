# ADR 001: стратегия хранения истории

**Статус:** принято.

## Контекст

В HW1 есть несколько разных типов изменяющихся данных. Одни атрибуты нужно уметь восстанавливать на историческую дату, другие важны только в текущем состоянии, а часть значений должна фиксироваться прямо в факте продажи.

Поэтому мы не используем одно универсальное правило «историзировать всё».

## Рассмотренные варианты

1. **Хранить только текущее состояние всех сущностей.** Отвергнуто: теряется историческая аналитика по SKU, клиентскому профилю и ценам.
2. **Историзировать каждое поле каждой сущности.** Отвергнуто: схема сильно усложняется без пользы для задания.
3. **Историзировать только явно изменяемые атрибуты и выбирать модель истории по типу данных.** Выбрано.

## Выбор

Используем несколько моделей истории.

### SKU

Стабильная идентичность хранится в `sku`.

Историзируем только атрибуты, про которые предметная область прямо говорит, что они меняются:

- `sku_name`;
- `category`;
- `is_rx`.

Они вынесены в `sku_version`.

Текущая версия определяется через `is_current=true`, а начало версии — через `valid_from`.

Не историзируем отдельно `manufacturer`, `drug_form`, `pack_qty`, `is_vital`, потому что в текущем scope задания нет явного требования восстанавливать их прошлые значения.

### Customer profile

Стабильная идентичность клиента хранится в `customer`.

Меняющийся профиль вынесен в `customer_profile_version`:

- город;
- регион;
- loyalty level.

Это позволяет восстанавливать исторический профиль клиента без переписывания основной customer row.

### Price

Для цены используем более строгую интервальную модель:

- `valid_from`;
- `valid_to`;
- `is_current`.

Цена зависит не только от SKU, но и от scope:

- chain;
- region;
- pharmacy.

Для одного `(sku, scope_type, scope_bk)` интервалы не должны пересекаться.

### Consent

Согласия сами по себе являются историческими фактами:

- тип;
- `issued_at`;
- `revoked_at`.

Поэтому отдельная version-table не нужна: каждая строка consent уже описывает период действия конкретного согласия.

### POS facts

Для продажи не пытаемся потом восстанавливать изменившийся Catalog по времени. Нужные значения фиксируются snapshot-полями в `receipt_line`.

Это отдельное решение и подробно описано в ADR про POS snapshots.

## Цена выбора

История хранится не одинаково во всех сущностях: где-то это version-table, где-то интервалы, где-то отдельные события, а где-то snapshot факта.

Это сложнее единой универсальной модели, но лучше соответствует реальной семантике данных и не заставляет историзировать поля без необходимости.
